# 4장: 민감 정보의 로컬 처리 및 사내 DB MCP — 요구사항 정의서 (PRD)

## 1. 개요 및 배경
- **장 목적**: 고객 DB(연락처, 계약 금액)를 조회하되 민감 정보는 절대 외부 상용 API로 전송되지 않도록, 로컬 LLM(`qwen3.5:9b`)을 이용한 가명화와 조회 전용 MCP 서버를 구축한다.
- **주요 독자 산출물**: SQLite 사내 DB, 조회 전용 MCP 서버(`src/mcp/server.py`), 로컬 가명화 필터(`src/mcp/redact.py`).

## 2. 세부 기능 요구사항
1. **사내 DB (SQLite)**:
   - 테이블: `customers`(고객명, 이메일, 전화번호, 회사명), `contracts`(계약ID, 고객ID, 계약금액, 계약일, 상태).
   - 권한: MCP 서버는 반드시 `READONLY` 모드로 DB 연결.
2. **조회 전용 MCP 서버**:
   - 도구 1: `query_customers(keyword)`: 고객 기본 정보 검색.
   - 도구 2: `query_contracts(customer_id)`: 계약 내역 검색.
3. **로컬 LLM 가명화 파이프라인 (Redaction)**:
   - Ollama `qwen3.5:9b` 모델을 로컬에서 호출하여 PII(주민번호, 전화번호, 이메일, 실명)와 계약 금액을 임의의 마스킹 토큰(`[고객A]`, `[연락처-XXX]`, `[금액-비공개]`)으로 변환.
   - 가명화가 완료된 안전한 텍스트만 상용 클라우드 에이전트로 전달.
4. **처리 태깅 (Logging & Tagging)**:
   - 모든 처리 데이터에 `route: "local"` 또는 `route: "api"` 메타데이터를 부여하여 JSONL 로그에 보존 (7장 대시보드 배지 표시의 원천).

## 3. 교차 검토 (Codex & Claude 협업 노트)
- **Codex**: GPU VRAM(12GB)에서 Ollama Qwen3.5:9B가 차지하는 메모리는 약 6.5GB이다. 5장의 Whisper와 동시 메모리 경합을 피하기 위해 4장 마지막 절에서 동시 구동 프로파일링을 선행 검증한다.
- **Claude**: "보안을 100% 보장한다"는 단정을 지양하고, 정규식 기반 1차 마스킹 + LLM 기반 2차 가명화의 이중 방어선 구조와 남은 위험을 솔직하게 서술한다.
